# ADR-002: Проектирование модели данных, полиморфных профилей и RBAC

* **Статус:** Принято (Accepted)
* **Дата:** 2026-10-06
* **Контекст:** Необходимость моделирования разнородных типов пользователей (студенты с академическими достижениями vs компании с вакансиями), безопасного разграничения доступа и воронки рассмотрения откликов.

---

## 1. Контекст и проблематика

В системе существуют три принципиально разные роли:
1. **Студент:** обладает академическими атрибутами (ВУЗ, факультет, курс, год выпуска, GPA, шкала GPA, олимпиады, научные статьи, курсовые проекты, GitHub).
2. **Работодатель / Рекрутер:** привязан к компании, управляет описанием стажировок, публикует вакансии и оценивает кандидатов.
3. **Администратор:** осуществляет модерацию контента и управление каталогами.

Требуется архитектурное решение для организации структуры БД, обеспечивающее:
* Изоляцию персональных данных и специфических полей ролей без денормализации в «гигантскую таблицу».
* Быструю и индексированную фильтрацию по академическим параметрам (GPA, ВУЗ, курс).
* Полную историю переходов статусов откликов кандидатов (аудит воронки).

---

## 2. Рассмотренные альтернативы

### Вариант А: Единая таблица `User` (Single Table Inheritance)
Все поля студента и компании хранятся в одной таблице с десятками `nullable` колонок.
* *Минусы:* Нарушение целостности, невозможность задать строгие ограничения `NOT NULL` на уровне схемы СУБД, риск утечки данных работодателя в студенческие выборки.

### Вариант Б: Полностью раздельные учетные записи (`StudentUser`, `EmployerUser`)
* *Минусы:* Дублирование логики аутентификации, сессий, токенов сброса пароля и OAuth-аккаунтов. Затрудняет сценарий, когда в будущем выпускник становится ментором или рекрутером.

### Вариант В: Базовая сущность `User` + специализированные профили (Profile Extension Pattern)
Базовая таблица `User` отвечает только за аутентификацию, системный статус и роль (`STUDENT`, `EMPLOYER`, `ADMIN`). С ней связаны отношениями `1-to-1` опциональные таблицы `StudentProfile` и `CompanyProfile`.

---

## 3. Решение

Принят **Вариант В**:

### 3.1. Структура профилей и RBAC
1. **Модель `User`:**
   * Содержит `email`, `passwordHash`, `role` (`STUDENT`, `EMPLOYER`, `ADMIN`), `status` (`ACTIVE`, `SUSPENDED`).
2. **Связанные профили:**
   * `StudentProfile` (1:1 к `User`): содержит академическую специфику (ВУЗ, факультет, направление, курс, год выпуска, статус поиска).
   * `CompanyProfile` (1:1 к `User`): содержит профиль компании (название, сайт, описание программ стажировок, логотип, статус верификации).

### 3.2. Моделирование академических сигналов (GPA и проекты)
* **Средний балл (GPA):**
  * Поля: `gpa: Float` и `gpaScale: Enum (SCALE_4, SCALE_5)`.
  * Нормализация: для фильтрации вводится вычисляемый или индексированный нормализованный балл (приведение к 100% или 4.0 шкале):
    $$\text{normalizedScore} = \begin{cases} \frac{\text{gpa}}{5.0} \times 4.0, & \text{если } \text{gpaScale} = 5.0 \\ \text{gpa}, & \text{если } \text{gpaScale} = 4.0 \end{cases}$$
* **Академические достижения:**
  * Отдельная сущность `AcademicAchievement` (связь 1:N со `StudentProfile`) с типами: `OLYMPIAD`, `PUBLICATION`, `CONFERENCE`, `HACKATHON`, `SCHOLARSHIP`.
* **Учебные и пет-проекты:**
  * Сущность `AcademicProject` (связь 1:N) с полями `title`, `description`, `repoUrl`, `technologies` (String[]).

### 3.3. Воронка откликов (Kanban) и аудит
* Статусы отклика:
  `NEW` → `SCREENING` → `TEST_TASK` → `INTERVIEW` → `OFFER` / `REJECTED`.
* Каждое изменение статуса фиксируется в таблице `ApplicationStatusHistory` (id, applicationId, changedByUserId, fromStatus, toStatus, note, changedAt) в рамках единой транзакции БД.

---

## 4. Индексация для производительности поиска

Для обеспечения быстрого поиска кандидатов создаются составные индексы в PostgreSQL:
* `@@index([university, currentCourse])` в `StudentProfile`
* `@@index([gpa, gpaScale])` в `StudentProfile`
* `@@index([status, publishedAt])` в `JobPosting`
* `@@index([jobPostingId, status])` в `JobApplication`
