# ADR-004: Стратегия тестирования и методология TDD для критических модулей

* **Статус:** Принято (Accepted)
* **Дата:** 2026-10-06
* **Контекст:** Обеспечение высокой надежности и безотказности критических сценариев (валидация академических данных, права доступа, жизненный цикл откликов) на основе методологии разработки через тестирование (TDD).

---

## 1. Контекст и проблематика

Платформа рекрутинга оперирует персональными данными студентов, конфиденциальной информацией компаний и критической бизнес-логикой воронки отбора кандидатов. Любые ошибки в правах доступа (например, студент видит чужие отклики) или расчете нормализованного GPA (несправедливый отсев талантливого кандидата) недопустимы.

Требуется стратегия тестирования, которая:
1. Гарантирует принцип **«Никакой новой функциональности без тестов»**.
2. Обеспечивает быстрый локальный фидбек для разработчиков и агентов (< 2 сек на юнит-тесты).
3. Покрывает сквозные сценарии пользователей от авторизации до оффера реальным браузером.

---

## 2. Пирамида тестирования

```text
         ▲
        / \         E2E Тесты (Playwright)
       /   \        - Сценарий 1: Студент (Регистрация -> Профиль -> Отклик)
      / E2E \       - Сценарий 2: Работодатель (Вакансия -> Фильтр GPA -> Смена статуса)
     /-------\
    / Интегра \     Интеграционные тесты (Vitest)
   /  ционные  \    - Сервисы (ApplicationService, VacancyFilterService)
  /-------------\   - Server Actions с проверкой прав доступа (RBAC)
 /  Модульные    \  Модульные тесты (Vitest)
/   (Unit)        \ - Zod-схемы валидации, расчет GPA, утилиты форматирования
-------------------
```

## 3. Выбор инструментов тестирования

| Слой тестирования | Инструмент | Обоснование выбора |
| :--- | :--- | :--- |
| **Unit & Integration** | **Vitest + React Testing Library** | Мгновенный старт благодаря нативному ESM/Vite, полная совместимость с синтаксисом Jest, быстрая параллелизация тестов |
| **E2E (End-to-End)** | **Playwright** | Кроссбраузерное тестирование (Chromium, Firefox, WebKit), устойчивость к асинхронным задержкам (auto-wait), встроенный генератор трассировок и видео |
| **Mocking БД / Сети** | **Prisma Mock / MSW** | Изоляция модульных тестов от реального сетевого соединения и базы данных |

## 4. Методология разработки TDD (Red-Green-Refactor)

Каждая задача по разработке бизнес-логики выполняется строго по следующим шагам:

1. **Этап Red (Красный):**
   * Разработчик или ИИ-агент создает файл спецификации (например, `tests/unit/gpa-calculator.test.ts` или `tests/integration/application-status.test.ts`).
   * Описываются тест-кейсы: допустимые границы GPA (0.0–5.0), недопустимые переходы статусов (нельзя перевести из `REJECTED` в `OFFER` без веских причин), проверка ошибки `UNAUTHORIZED` при попытке неавторизованного отклика.
   * Тест запускается: `npm run test` → результат **FAIL**.

2. **Этап Green (Зеленый):**
   * Реализуется минимальный код в сервисе/валидаторе/экшене, достаточный для прохождения тестов.
   * Тест запускается: `npm run test` → результат **PASS**.

3. **Этап Refactor (Рефакторинг):**
   * Оптимизируется структура кода, устраняется дублирование, проверяется соблюдение TypeScript-типов.
   * Все тесты запускаются повторно: гарантируется отсутствие регрессий.

## 5. Спецификация ключевых E2E-сценариев (Playwright)

### Сценарий 1: Жизненный цикл кандидата-студента
1. Переход на страницу регистрации (`/register`).
2. Создание аккаунта с ролью `STUDENT`.
3. Заполнение академического профиля: ВУЗ («МГТУ им. Баумана»), специальность («Информатика и ВТ»), 3 курс, GPA `4.9` (шкала 5.0), добавление проекта со ссылкой на GitHub.
4. Переход в каталог вакансий (`/vacancies`).
5. Фильтрация по критериям «Стажировка» и «Наличие ментора».
6. Открытие детальной страницы вакансии, ввод сопроводительного письма и отправка отклика.
7. Проверка появления отклика в личном кабинете студента со статусом `Новый`.

### Сценарий 2: Жизненный цикл работодателя
1. Авторизация работодателя (`/login`).
2. Создание новой вакансии с академическими фильтрами: мин. курс = 3, мин. GPA = 4.5.
3. Открытие списка входящих кандидатов.
4. Применение фильтра по ВУЗу и GPA.
5. Просмотр академического резюме кандидата.
6. Перевод отклика через стадии: `Новый` → `Скрининг` → `Тестовое задание` → `Интервью` → `Оффер`.
7. Проверка сохранения истории изменений в аудит-логе.

---

## 6. Метрики качества и правила CI

* **Покрытие кода (Coverage):** минимум **85%** для модулей валидации (`lib/validations/`) и сервисной бизнес-логики (`server/services/`).
* **CI Gate:** Ни один Pull Request не может быть влит без 100% успешного прохождения unit/integration тестов и прохождения базового набора Playwright-тестов.
